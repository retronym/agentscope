# PLAN: the profiler in the live demo

## Why

The README and the demo undersell the JVM profiler, Across JVMs above all. The demo shows only the hsperfdata table: Record, Activity, a JVM's full view (heatmap, lanes, flame graph) and Across JVMs are hidden in demo mode, and the README carries hand-taken screenshots that fall behind the UI (the latest flame graph controls aren't in any of them). A demo that has the profiler working, with real stacks, sells it better than more screenshots, and keeps the screenshots honest because they're generated from it.

## Key decisions

- **Real stacks from a public workload, not invented ones and not the user's own.** Made-up stacks look fake once you zoom in; the user's recorded stacks would leak private class and package names that a denylist can't reliably catch. Recording JVMs that build public code (sbt compiling and testing a generated Scala project, javac) gives real depth, recursion and activity labels with nothing to anonymize.
- **Recorded once, committed as a fixture.** `mise run demo-fixture` records the workload with agentscope's own helper and writes a compact, subsampled fixture. `mise run demo` stays quick and needs no JDK.
- **The page computes profile answers itself in demo mode**, from the fixture, like the rest of the static demo (`staticApi`): a JVM's summary, flame graph, activity lanes, and Across JVMs. Flame graph filters, search and highlights already run in the browser, so the latest flame graph UI comes for free.
- **Across JVMs history comes from the snapshot's own process history.** Every JVM-looking process in the anonymized week of history gets the fixture's minutes for a workload like its own, scaled by its real CPU that minute. Session → JVM → activity is then shaped like the real week, and the frames are public.
- **The demo clock ticks.** The fixture loops, so lanes and heatmaps move like a live page.

## Steps

- [x] 1. Helper op to dump a recording's raw profile; `demo/record_fixture.py` runs the workload, records it, writes `demo/fixture/profiles.json.gz`; `mise run demo-fixture`.
- [x] 2. `static/demo.js`: fixture-backed summary, flame, thread activity and Across JVMs, with the same shapes and pruning as the helper and `profiles.flame`.
- [x] 3. Export: fixture JVMs assigned to the demo's live agent JVMs, recording state in `state.record`, Across JVMs history from process history; the page shows Record (inert), Activity, the full view's profile and Across JVMs in demo mode.
- [x] 4. Screenshots of the JVM views generated by `demo/screenshots.py`.
- [x] 5. README: pitch the profiler, Across JVMs first; trim what the demo now shows.

Along the way, rough edges found by driving the profiler on these workloads, fixed:

- sbt runs its tasks on short-lived pool threads (1,700 in five minutes), so lanes were dozens of one-blip rows. Threads of a group (`pool-*-thread-*`, `worker-*`) now share a lane, in a JVM's full view and in Activity; clicking one filters the flame graph to the group (the helper's `flame` takes `group`). Activity's "busy now" lines group the same way.
- Across JVMs split its JVM level by pid, so a session that restarted sbt thirty times in a week showed thirty slivers. The level is now the kind of JVM (`sbt server`, `javac`).
- `#only=` takes a part of a section (`#only=jvmflame`), and `#across=<seconds>` sets Across JVMs' range, for screenshots and links.

Noticed, not fixed:

- JFR on macOS delivers roughly a quarter of its nominal execution samples, with agentscope's settings and with JFR's own `profile` settings alike.
- The stored stack pool (`node`) is never pruned and grows with deep, varied stacks: about 6M nodes, 110 MB, for 92 recorded minutes here, against 0.6 MB of sample blobs.
